// 01 · PROBLEM

招聘评估的五个死结

简历筛不完 · 真假说不清 · 面试结论和材料对不上

01

简历全是自述

内容主要由候选人自己写，真实性与个人贡献难以直接判断，HR 只能凭经验猜测。

02

关键词匹配误判

不同岗位能力要求差异大，单纯的关键词命中很容易把"写过"当成"做成过"。

03

外部核验成本高

项目、论文、专利、奖项等资料分散在各处，人工逐条核验几乎不可行。

04

AI 分数不可信

缺少证据定位、计算规则与人工复核机制的评分，无法用于严肃的招聘决策。

05

面试与简历割裂

面试结论不回流到材料层，候选人的补充说明与矛盾信息难以形成闭环。

// 02 · PRINCIPLES

双账本，不制造单一"人才总分"

证据可信度 ≠ 岗位适配度，两者不能简单相加

LEDGER A

证据可信度

材料是否有外部佐证、来源质量如何、信息是否一致。

LEDGER B

岗位适配度

候选人现有证据对岗位能力要求的支持程度。

supportedpartial not_enoughcontradicted

⚠ 证据少不等于能力差；证据充分也不必然代表岗位适配。

01 · 回到证据

每项判断关联 Claim / Evidence / 原文摘录或面试轮次；无法定位依据的结论标记为待验证。

02 · 规则负责计算

LLM 只做抽取、归纳、生成与解释；分数由可版本化、可测试的规则与权重方案计算。

03 · 人工复核优先

低置信匹配、事实冲突、证据不足与高影响结论进入人工复核；修改留痕可追溯。

04 · 授权是业务能力

语音面试须服务端二次核验授权；撤回即阻断；删除覆盖文件、文本、转写、向量与缓存。

// 05 · WORKFLOW

从 JD 到报告的六步闭环

每一步都可定位、可回放、可人工修订

STEP 01

岗位画像生成

JD 录入或 AI 生成润色 → 结构化抽取 → 能力维度与权重方案 → HR 确认发布。已发布版本不可原地覆盖。

STEP 02

简历解析与 Claim 抽取

文件入对象存储 → 解析任务 → 教育/工作/项目/论文/专利/奖项/技能拆解为 Claims，保留字符偏移与来源版本。

STEP 03

实体识别与证据核验

公司/学校/项目/论文/专利/奖项实体 → 消歧 → 白名单来源检索 → 来源快照与哈希 → 证据分级。

STEP 04

岗位适配评估

岗位要求映射到能力维度 → 关联支持/反向/缺失证据 → 规则引擎计算维度分 → 独立计算证据可信度。

STEP 05

授权式语音面试

候选人选择授权范围 → 服务端二次核验 → 依据证据缺口生成问题计划 → 实时语音会话。

STEP 06

交叉核验与报告

面试回答与简历 Claims 比对 → 一致/补充/冲突/待核验 → 追问建议与人工复核事项。

证据分级

证据链三级核验 核心

L1

成果存在性

项目、论文、专利或奖项，是否真实存在？——可由外部页面 / 官方数据库佐证。

L2

个人参与性

候选人是否确实参与该成果？——需要署名、贡献者列表、代码提交等多源交叉。

L3

个人贡献度

具体承担了什么工作、产生了什么可归因贡献？——最难，通常需要面试补充验证。

⚠ 外部页面证明项目存在，并不能自动证明候选人参与，更不能自动证明其贡献程度。

含金量建模维度

学校 / 专业

不同年份、不同专业的培养质量与学科实力变化，而非简单院校标签。

公司 / 部门

区分公司整体与具体部门、业务线在不同年份的含金量差异。

团队 / 项目

项目规模、影响力、公开可查的落地成果与开源活跃度。

论文 / 专利 / 奖项

收录情况、引用、发明人排序、奖项等级与授予机构权威性。

// 08 · ASSESSMENT

三个独立观察面

不要把它们压缩成同一个分数

0

Evidence Confidence

当前材料可信程度如何？

0

Capability Assessment

证据对某项岗位能力提供多强支持？

0

Assessment Coverage

本次评估覆盖了多少关键维度？

建议的报告结构 JSON

{
  "evidence_assessment": { "score": 0, "grade": "B", "coverage": 0, "limitations": [] },
  "job_match":        { "score": 0, "dimensions": [] },
  "assessment_quality": {
    "comparable": false,
    "coverage": 0,
    "evidence_sufficiency": "low",
    "uncertainty_level": "high",
    "missing_dimensions": []
  },
  "verification_tasks": [],
  "human_review_required": true
}

引用校验失败即降级

报告中的每条结论都必须能校验到证据引用；校验失败时降级或拒绝输出该结论。

低覆盖不可直接比较

低覆盖或低证据充分度的评估，标记为"不宜直接比较 / 待补充核验"。

规则版本化

权重、阈值、提示词、模型与数据版本全部留痕，支持回归测试与版本对比。

// 09 · SECURITY

安全、隐私与合规

简历、网页、API 返回与语音转写，全部视为不可信数据

🔒 多租户隔离

所有租户归属明确的业务表统一检查 tenant_id：组合外键 + PostgreSQL RLS + API 层上下文校验 + 跨租户访问自动化测试 + 后台任务显式传递租户上下文。

🛡 提示词注入防护

简历、附件、超链接、GitHub README、论文页面、外部 API 返回、候选人语音转写均为不可信数据；其中的指令不得作为系统指令执行。工具调用使用白名单、最小权限与结构化参数校验。

🗑 授权与删除

语音面试前校验授权目的、范围、版本与有效期；撤回后终止相关处理。删除覆盖对象存储、数据库、搜索/向量索引、缓存与第三方链路，并做抽样或自动化验证。

⚖️ 招聘公平性

不得仅凭年龄、性别、种族、宗教、婚育状况、院校标签或口音等敏感/代理特征作出能力判断。表达流畅度不能替代技术能力。分群误差审查 + 人工复核 + 申诉纠错。

// 10 · ROADMAP

V1.1 完善与创新路线图

先盘点当前实现，确认已有能力、缺口和兼容风险，再按优先级迭代——不推翻重写

P0

可靠性与评估可信度

  • 统一解析状态机，消除 done / parsed / partial / error 语义不一致
  • 审查核心业务表的 tenant_id、组合外键、RLS 与跨租户访问测试
  • 建立 Assessment Snapshot：固定简历版本、岗位版本、权重方案、提示词/模型/规则版本与证据快照
  • 三个观察面分开呈现；低覆盖评估增加"不宜直接比较"状态
  • 评分规则增加边界保护、缺失值处理、冲突识别与版本化
P1

人才能力认知与贡献核验

  • 建立统一 Competency Dictionary，打通岗位、简历、面试与评估维度
  • 三级贡献证据链：成果存在性 → 个人参与性 → 个人贡献度
  • Transferable Skills 识别，区分直接证据、相关证据与待验证推断
  • 人才能力关系模型：Person / Skill / Competency / Project / Achievement / Organization / Role / Evidence
  • 初期在 PostgreSQL 用关系表实现，不因"知识图谱"概念过早引入图数据库
P2

主动式评估与人才发现

  • Assessment Orchestrator：统一调度解析、核验、评估、面试计划与报告更新
  • Assessment Planner：依据岗位关键能力缺口生成下一步验证任务
  • 有边界的 Agent 工作流：只能在授权工具、数据范围与状态机约束内执行
  • 多候选人能力矩阵；候选人 ↔ 岗位双向推荐
P3

模型评测与持续校准

  • 抽取准确率、实体消歧准确率、证据匹配准确率、评分一致性评测集
  • 人工标注规范与双人复核抽样机制
  • 真实岗位样本 + 招聘专家评审，校准权重与阈值
  • 监控不同岗位类别与群体的误差差异，发现偏差时暂停相关自动化结论

技术栈与工程约束

API 约定

前缀 /api/v1；写接口支持 Idempotency-Key；PATCH 使用 If-Match；响应带 X-Request-Id。

贡献与维护

已知边界
